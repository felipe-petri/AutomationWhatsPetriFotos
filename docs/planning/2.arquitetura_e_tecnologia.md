# 02 — Arquitetura e Stack Tecnológica

> **Stack definida:** Node.js (v20+ LTS) + TypeScript (Strict Mode) + Fastify + PostgreSQL 16 + Redis + Evolution API v2 (Baileys/Docker) + Zod + Vitest.
>
> **Regra de ouro:** Nenhuma mensagem do WhatsApp é processada diretamente no ciclo de vida da requisição HTTP. O webhook da Evolution API responde `200 OK` imediatamente (ACK em $< 150\text{ ms}$) após validação básica de assinatura e enfileira o evento no Redis/BullMQ. O processamento das regras de negócio do estúdio ocorre de forma assíncrona, desacoplada e 100% testável, garantindo idempotência e isolamento de falhas.

## 2. Decisões Técnicas por Camada

### 2.1 Camada de Ingestão e Webhook

| Tema | Decisão Técnica | Justificativa de Engenharia |
| :--- | :--- | :--- |
| **Framework HTTP** | Fastify (v4.x) | Baixo overhead de CPU e alta vazão para I/O, ideal para absorver picos de webhooks de mensagens simultâneas. |
| **Contrato de Ingestão** | Zod (Strict Object Schema) | Validação em tempo de execução dos formatos de evento (`MESSAGES_UPSERT`, `CONNECTION_UPDATE`). Falhas no schema geram log e descarte imediato sem quebrar a aplicação. |
| **Segurança do Webhook** | Assinatura no Header (`apiKey`) | A Evolution API envia a chave global em `apikey`. O Fastify valida via middleware `preHandler` com tempo constante (`crypto.timingSafeEqual`) para evitar timing attacks. |
| **Estratégia de ACK** | `HTTP 200 {"status":"queued"}` | A Meta e o Baileys retransmitem eventos se o endpoint demorar $> 2000\text{ ms}$. Respondendo em $< 150\text{ ms}$, eliminamos tempestades de retransmissão de mensagens. |

### 2.2 Orquestração, Mensagens Customizáveis e FSM

| Tema | Decisão Técnica | Justificativa de Engenharia |
| :--- | :--- | :--- |
| **Padrão de Navegação** | FSM baseada em estados relacionais | Cada usuário possui um único registro em `sessions` com `current_state` e `context_data`. Elimina fluxos aninhados e `if/else` espaguete. |
| **Motor de Mensagens** | `PromptEngine` (`src/config/messages.json`) | Nenhuma mensagem textual, prazo ou preço fica *hardcoded*. O estúdio pode ajustar redações, prazos e avisos sem alterar o código. |
| **Deduplicação / Idempotência** | Redis Key com TTL (`SETNX`) | Cada `key = idempotency:msg:${messageId}` expira em 10 minutos. Mensagens repetidas são descartadas com log sem consumir banco relacional. |
| **Concorrência por Usuário** | Mutex distribuído via Redlock | Se o cliente mandar 3 mensagens ou áudios seguidos, o sistema processa um por vez em sequência, evitando que o estado seja sobrescrito concorrentemente. |
| **TTL de Inatividade** | 30 minutos | Se o cliente abandonar o atendimento pela metade, o estado reseta para `IDLE` na próxima mensagem, evitando que uma saudação caia no meio de um formulário quebrado. |
| **Transbordo Humano** | Flag `HUMAN_ATTENDANCE` no banco | Ativado via palavra-chave ("atendente", "humano", "0") ou fallback (2 erros consecutivos). O bot silencia e notifica a equipe do estúdio. |

### 2.3 Módulos de Domínio da Petri Fotos

| Módulo | Regras de Negócio e Implementação |
| :--- | :--- |
| **Fotos para Documento** | Preço fixo de R$ 30,00 para qualquer formato ($3\times4$, $3.5\times4.5$, $5\times5$, $5\times7$). Quantidades: 6 unidades para $3\times4$ e $3.5\times4.5$; 2 unidades para $5\times5$ e $5\times7$. Atendimento presencial por ordem de chegada no estúdio em horário comercial. **Não há Pix antecipado nem agendamento prévio**. |
| **Catálogos em PDF (11 Categorias)** | Disparo automático de arquivos PDF organizados em 3 grupos: (1) Maternidade & Bebê (Gestante, Newborn, Acompanhamento, Revelação); (2) Comemorações (Aniversário Infantil, 15 Anos, Batizado); (3) Estúdio & Carreira (Família, Formatura em Estúdio, Perfil Profissional). Registra lead qualificado internamente. |
| **Revelações de Fotos Pessoais** | **Pix antecipado obrigatório**. O bot orienta envio das fotos pelo chat como documento, contabiliza os tamanhos ($10\times15$, $15\times21$, etc.) e emite o Pix Copia e Cola. A produção no laboratório só inicia após confirmação do pagamento. |
| **Galeria Digital Alboom** | Assistido com SLA: ao solicitar o link, o bot avisa que a equipe precisa de **algumas horas** para upload/tratamento e que o link será enviado manualmente pelo WhatsApp. Ao cliente confirmar a escolha de fotos, o bot formaliza o prazo de produção de **até 10 dias úteis**. |
| **Eventos Sacramentais** | Coleta de dados (nome da criança/adolescente, paróquia/igreja, ano do evento). **Sem cobrança no WhatsApp**, pois as fotos de Primeira Comunhão, Crisma e Confirmação contratadas na cerimônia já foram quitadas previamente. |

## 3. Padrão de Implementação (Pseudocódigo TypeScript)

### 3.1 Handler de Ingestão e Enfileiramento

```typescript
// src/modules/webhook/webhook.controller.ts
import { FastifyRequest, FastifyReply } from 'fastify'
import { z } from 'zod'
import { messageQueue } from '../../shared/queues/message.queue'

const EvolutionEventSchema = z.object({
  event: z.string(),
  instance: z.string(),
  data: z.object({
    key: z.object({
      remoteJid: z.string(),
      fromMe: z.boolean(),
      id: z.string()
    }),
    pushName: z.string().optional(),
    message: z.record(z.unknown()).optional(),
    messageTimestamp: z.number().or(z.string())
  })
})

export async function evolutionWebhookHandler(
  request: FastifyRequest,
  reply: FastifyReply
): Promise<void> {
  const parseResult = EvolutionEventSchema.safeParse(request.body)

  if (!parseResult.success) {
    return reply.status(200).send({ ignored: true, reason: 'schema_mismatch' })
  }

  const { event, data } = parseResult.data

  if (data.key.fromMe || event !== 'messages.upsert') {
    return reply.status(200).send({ ignored: true })
  }

  await messageQueue.add(
    'process-incoming-message',
    {
      messageId: data.key.id,
      remoteJid: data.key.remoteJid,
      senderName: data.pushName ?? 'Cliente',
      rawPayload: data.message,
      timestamp: Number(data.messageTimestamp)
    },
    {
      jobId: data.key.id,
      removeOnComplete: true,
      attempts: 3,
      backoff: { type: 'exponential', delay: 1000 }
    }
  )

  return reply.status(200).send({ received: true })
}
```

### 3.2 Processador de FSM, Prompts Customizáveis e Idempotência

```typescript
// src/core/fsm/conversation-worker.ts
import { Job } from 'bullmq'
import { redisClient } from '../../shared/database/redis'
import { sessionRepository } from '../../modules/sessions/session.repository'
import { fsmRouter } from './fsm.router'
import { evolutionClient } from '../../shared/clients/evolution.client'

interface IncomingMessageJob {
  messageId: string
  remoteJid: string
  senderName: string
  rawPayload: Record<string, unknown>
  timestamp: number
}

export async function processConversationJob(job: Job<IncomingMessageJob>): Promise<void> {
  const { messageId, remoteJid, rawPayload, senderName } = job.data

  // 1. Guard de Idempotência
  const lockAcquired = await redisClient.set(
    `idempotency:msg:${messageId}`,
    'processed',
    'EX',
    600, // 10 minutos
    'NX'
  )

  if (!lockAcquired) {
    return
  }

  // 2. Trava de concorrência por contato (15 segundos)
  const userLockKey = `lock:user:${remoteJid}`
  const userLock = await redisClient.set(userLockKey, 'locked', 'EX', 15, 'NX')
  if (!userLock) {
    throw new Error(`Concorrência detectada para ${remoteJid}. Job voltará para retry.`)
  }

  try {
    // 3. Recuperação de Sessão
    let session = await sessionRepository.findByRemoteJid(remoteJid)
    if (!session) {
      session = await sessionRepository.create(remoteJid, senderName)
    }

    // 4. Verificação de Transbordo Humano
    if (session.currentState === 'HUMAN_ATTENDANCE') {
      return
    }

    // 5. Execução de Transição na Máquina de Estados (usa strings do messages.json)
    const textInput = extractMessageText(rawPayload)
    const transitionResult = await fsmRouter.execute({
      session,
      textInput,
      rawPayload
    })

    // 6. Atualiza Estado e Contexto no PostgreSQL
    await sessionRepository.update(remoteJid, {
      currentState: transitionResult.nextState,
      contextData: transitionResult.updatedContext,
      lastInteractionAt: new Date()
    })

    // 7. Disparo da Resposta via Evolution API (Texto ou PDF)
    if (transitionResult.mediaAttachment) {
      await evolutionClient.sendMediaMessage({
        remoteJid,
        mediaUrl: transitionResult.mediaAttachment.url,
        caption: transitionResult.replyMessage,
        fileName: transitionResult.mediaAttachment.fileName
      })
    } else {
      await evolutionClient.sendTextMessage({
        remoteJid,
        text: transitionResult.replyMessage
      })
    }
  } finally {
    await redisClient.del(userLockKey)
  }
}
```

## 4. Estratégia e Arquitetura de Testes

Para garantir que nenhuma alteração quebre o fluxo de atendimento nem envie mensagens erradas para os clientes, o projeto adota uma suíte de testes com **Vitest** estruturada em três níveis:

```
        / \
       / E2E \       (Simulação do fluxo completo de webhook com Supertest e Mock da Evolution)
      /-------\
     / Integr. \     (Transições FSM + Sessões PostgreSQL + Idempotência no Redis)
    /-----------\
   /   Unitários \   (Cálculo de preços, validadores Zod, motor de prompts)
  /---------------\
```

### 4.1 Testes Unitários (`tests/unit/`)
* **`pricing-engine.spec.ts`:**
  * Valida que qualquer formato de foto para documento retorna exatamente R$ 30,00.
  * Valida que o lote de fotos pessoais calcula a soma correta das quantidades e dimensões.
* **`prompt-engine.spec.ts`:**
  * Garante que `src/config/messages.json` é carregado sem chaves nulas ou ausentes.
  * Valida a injeção correta de placeholders dinâmicos (ex: `{PIX_COPIA_E_COLA}`, `{PRAZO_DIAS}`).
* **`zod-schemas.spec.ts`:**
  * Rejeita webhooks malformados ou sem `remoteJid` válido.

### 4.2 Testes de Integração (`tests/integration/`)
* **`fsm-transitions.spec.ts`:**
  * Testa o ciclo completo de navegação do menu (Menu Principal $\to$ Opção 2 $\to$ Envio de PDF de Gestante).
  * Simula a transição para `HUMAN_ATTENDANCE` ao digitar "0" ou "atendente" e verifica o bloqueio de respostas subsequentes.
* **`idempotency.spec.ts`:**
  * Envia o mesmo `messageId` duas vezes contra o Redis e confirma que o segundo evento é descartado sem invocar a FSM.
* **`session-timeout.spec.ts`:**
  * Simula uma sessão inativa há 31 minutos e valida o reset automático para `IDLE`.

### 4.3 Testes Ponta a Ponta / E2E (`tests/e2e/`)
* **`webhook-flow.spec.ts`:**
  * Dispara requisição HTTP `POST /webhook/evolution` via Supertest.
  * Valida resposta imediata `HTTP 200` com `{ "received": true }` em $< 150\text{ ms}$.
  * Utiliza mock (`vi.spyOn`) do cliente Evolution para verificar se o payload de saída continha o PDF correto ou o texto configurado.

## 6. Modelagem de Dados Relacional (PostgreSQL)

```sql
-- Sessões ativas e máquina de estados
CREATE TABLE sessions (
    remote_jid VARCHAR(64) PRIMARY KEY,
    sender_name VARCHAR(128) NOT NULL,
    current_state VARCHAR(64) NOT NULL DEFAULT 'IDLE',
    context_data JSONB NOT NULL DEFAULT '{}'::jsonb,
    error_count INT NOT NULL DEFAULT 0,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Tabela de idempotência persistente (fallback além do Redis)
CREATE TABLE idempotent_messages (
    message_id VARCHAR(128) PRIMARY KEY,
    remote_jid VARCHAR(64) NOT NULL,
    processed_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Pedidos formais de impressão de fotos pessoais (com Pix obrigatório)
CREATE TABLE print_orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    remote_jid VARCHAR(64) NOT NULL REFERENCES sessions(remote_jid),
    total_amount NUMERIC(10, 2) NOT NULL,
    pix_code TEXT,
    payment_status VARCHAR(32) NOT NULL DEFAULT 'PENDING_PIX', -- 'PENDING_PIX', 'PAID', 'CANCELLED'
    items JSONB NOT NULL DEFAULT '[]'::jsonb, -- lista de fotos, tamanhos e quantidades
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Solicitações de galerias Alboom (SLA assistido)
CREATE TABLE alboom_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    remote_jid VARCHAR(64) NOT NULL REFERENCES sessions(remote_jid),
    client_name VARCHAR(255) NOT NULL,
    session_approx_date VARCHAR(64),
    status VARCHAR(32) NOT NULL DEFAULT 'AWAITING_UPLOAD', -- 'AWAITING_UPLOAD', 'LINK_SENT', 'SELECTION_CONFIRMED'
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    selection_confirmed_at TIMESTAMP WITH TIME ZONE,
    production_deadline_at DATE
);

-- Registros de dados de Crisma / Eucaristia (Quitados antecipadamente)
CREATE TABLE sacramental_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    remote_jid VARCHAR(64) NOT NULL,
    student_name VARCHAR(255) NOT NULL,
    church_name VARCHAR(255) NOT NULL,
    event_year VARCHAR(10) NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'RECEIVED',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE INDEX idx_sessions_updated_at ON sessions(updated_at);
CREATE INDEX idx_print_orders_remote_jid ON print_orders(remote_jid);
```

## 7. Checklist de Segurança e Governança (LGPD)

- [ ] **Isolamento de Credenciais:** As chaves de API da Evolution API e credenciais de banco residem exclusivamente em variáveis de ambiente, nunca commitadas no Git.
- [ ] **Expurgo de Fotos de Impressão Pessoal:** Arquivos de fotos pessoais recebidas via chat para revelação devem ser removidas do storage local em até 48 horas após a produção do pedido, respeitando os princípios de minimização da LGPD.
- [ ] **Proteção de Dados Sacramentais de Menores:** Dados de menores coletados no módulo sacramental (nome, paróquia, fotos) são classificados como dados sensíveis e acessíveis apenas pelo operador do estúdio via painel interno autenticado.
- [ ] **Rate Limiting por Contato:** Bloqueio temporário (15 minutos) para números que dispararem $> 20$ requisições/mensagens por minuto, prevenindo ataques de negação de serviço ao webhook.

## 9. Fluxo Git e Política de Pull Requests

1. A branch `main` é permanentemente protegida contra commits diretos.
2. Nenhuma alteração sobe sem aprovação mútua via **Pull Request (PR)**.
3. O workflow de CI (`ci.yml`) executa compilação estrita (`tsc --noEmit`), linter (`eslint`) e a suíte completa de testes (`vitest run`) antes de autorizar qualquer merge.
