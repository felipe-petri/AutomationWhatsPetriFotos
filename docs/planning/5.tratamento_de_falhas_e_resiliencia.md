# 05 — Tratamento de Falhas e Resiliência

> **Objetivo:** Estabelecer mecanismos de tolerância a falhas, garantias de entrega, idempotência, recuperação automática de estado e contingência operacional para o sistema `automationWhatsPetri`.

---

## 1. Princípios de Resiliência do Sistema

A automação de WhatsApp opera sobre uma rede assíncrona, instável e de alto volume de retransmissões. A arquitetura adota cinco preceitos fundamentais:

1. **Ingestão Desacoplada (Fast ACK):** O recebimento do webhook nunca depende do processamento da regra de negócio. O socket HTTP da Evolution API é liberado em $< 150\text{ ms}$.
2. **Idempotência em Duas Camadas:** Nenhuma mensagem é processada mais de uma vez, mesmo em oscilações de rede da operadora ou do Baileys.
3. **Isolamento de Concorrência por Contato:** Um mutex distribuído por `remoteJid` impede processamento cruzado caso o cliente envie múltiplos áudios ou textos em sequência rápida.
4. **Degradação Graciosa:** Se um serviço externo falhar (ex.: geração de Pix ou Alboom), o bot informa a indisponibilidade temporária e oferece transbordo humano sem travar a sessão.
5. **Máquina de Estados Auto-Reparadora (Self-Healing FSM):** Sessões inativas há mais de 30 minutos ou presas em ciclos de erro retornam de forma determinística para o estado inicial (`IDLE`).

## 2. Garantias de Idempotência e Deduplicação

```
Webhook Evolution API
         │
         ▼
[ Extrai messageId ]
         │
         ▼
┌──────────────────────────────────────────────┐
│ Camada 1: Cache Atômico em Redis (Memória)  │
│ Comand: SET idempotency:msg:{id} 1 NX EX 600 │
└──────────────────────┬───────────────────────┘
                       │
          ┌────────────┴────────────┐
          ▼ Existe                  ▼ Não Existe (Chave gravada)
     [ DESCARTA ]             [ PROCESSA MENSAGEM ]
     Log: duplicata                   │
                                      ▼
                      ┌─────────────────────────────────┐
                      │ Camada 2: Persistência no Banco │
                      │ INSERT INTO idempotent_messages │
                      │ ON CONFLICT (message_id) DO ... │
                      └─────────────────────────────────┘
```

### Regras de Descarte:
* **Redis `SET ... NX EX 600`:** Garante deduplicação instantânea de alta performance com retenção de 10 minutos (janela típica de retransmissão de webhooks).
* **Fallback no PostgreSQL (`idempotent_messages`):** Usado para auditoria e histórico de longo prazo. Em caso de reinicialização do Redis, o banco atua como barreira secundária de integridade.

## 3. Estratégia de Concorrência e Locks (Race Conditions)

Quando um cliente envia 3 mensagens consecutivas (ex.: "Olá", "Quero 3x4", "Quanto fica?"), o WhatsApp dispara 3 webhooks quase simultâneos.

* **Mutex Distribuído:** Antes de carregar o estado do usuário, o worker tenta obter um lock:
  $$\text{Chave: } \texttt{lock:user:\{remoteJid\}} \quad (\text{TTL: } 15\text{ s})$$
* **Comportamento em Bloqueio:** Se o lock já estiver ocupado pelo processamento da primeira mensagem, o job correspondente no BullMQ faz um *release com backoff* e retorna para a fila com atraso de $1000\text{ ms}$, garantindo que as mensagens sejam consumidas em ordem estrita de chegada.

## 4. Gestão de Instabilidades na Evolution API e WhatsApp

| Cenário de Falha | Diagnóstico Técnico | Ação Automática de Recuperação |
| :--- | :--- | :--- |
| **Queda do WebSocket da Evolution** | Evento `connection.update` com status `close` ou desconexão Baileys. | Worker interno emite log crítico e aguarda o mecanismo nativo de auto-reconnect do container. O bot não envia mensagens e enfileira as saídas com TTL de 5 minutos. |
| **Timeout de Envio de Mensagem ($> 5\text{ s}$)** | Chamada HTTP para `POST /message/sendText` retorna $504$ ou aborta por socket hang up. | O client aplica **Exponential Backoff com Jitter** ($1\text{ s}, 2\text{ s}, 4\text{ s}$). Após 3 tentativas frustradas, a mensagem cai na Dead Letter Queue (DLQ). |
| **Circuit Breaker Aberto na Evolution** | 5 erros consecutivos $5xx$ na API do WhatsApp. | Abre o circuito por 30 segundos. Chamadas subsequentes falham de imediato sem sobrecarregar o container, logando o incidente e alternando para modo de segurança. |

## 5. Falhas no Fluxo de Negócio e Transbordo Humano

A máquina de estados possui proteções ativas contra loops de incompreensão do usuário:

```
[ Usuário envia entrada ] ──► [ Validação contra o Estado Atual ]
                                         │
                         ┌───────────────┴───────────────┐
                         ▼ Válido                        ▼ Inválido
                  [ Transita FSM ]              [ Incrementa error_count ]
                  [ error_count = 0 ]                    │
                                                         ▼
                                                error_count >= 2?
                                                ├── Não: Reenvia pergunta
                                                └── Sim: Aciona Fallback
                                                         │
                                                         ▼
                                            [ state = HUMAN_ATTENDANCE ]
                                            [ Dispara Notificação Estúdio ]
                                            [ Mensagem de Encaminhamento ]
```

### Regras de Transbordo:
1. **Contador de Erros:** Se o cliente fornecer uma entrada inválida por duas vezes consecutivas em qualquer submenu, o bot não insiste. Ele responde:
   > *"Percebi que posso não ter compreendido bem o que você precisa. Já transferi seu atendimento para nossa equipe da Petri Fotos. Em breve um atendente falará com você por aqui!"*
2. **Silenciamento Imediato:** O estado `HUMAN_ATTENDANCE` bloqueia o processamento de novas respostas automáticas do bot.
3. **Reset de Sessão:** O operador humano pode resetar a sessão enviando o comando interno `#reset` pelo próprio chat ou via painel, ou a sessão expira automaticamente após 2 horas sem novas mensagens.

## 6. Dead Letter Queue (DLQ) e Políticas de Retry

Todas as tarefas assíncronas executadas via BullMQ seguem uma política formal de reprocessamento:

* **Fila Principal (`incoming-messages`):**
  * `attempts`: 3 tentativas.
  * `backoff`: Exponencial iniciando em $1000\text{ ms}$ com multiplicador $2$.
* **Fila de Falha Irrecuperável (`messages-dlq`):**
  * Armazena payloads que falharam após todas as tentativas.
  * Mantém o erro original, stack trace e contexto da sessão para inspeção do desenvolvedor.
  * Endpoint interno protegido `POST /admin/queues/retry-dlq` permite reprocessar lotes após correção de eventuais bugs.

## 7. Políticas de Reinicialização de Containers (Docker)

No arquivo `infra/docker-compose.yml`, todos os serviços essenciais contêm regras de sobrevivência e limites de recurso:

```yaml
restart: unless-stopped
deploy:
  resources:
    limits:
      cpus: '1.0'
      memory: 1024M
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres || exit 1"]
  interval: 10s
  timeout: 5s
  retries: 5
```

* **Comportamento em Crash:** Se a aplicação Node.js sofrer uma falha de memória não tratada (`OOM`) ou exceção fatal, o daemon do Docker reinicia o container automaticamente em $< 3\text{ s}$.
* **Proteção de Estado em Reboot:** As sessões ativas continuam íntegras no PostgreSQL; nenhuma informação de pedido ou agendamento em andamento reside exclusivamente na memória RAM da aplicação.
